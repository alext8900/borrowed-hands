# Borrowed Hands protocol v1

**Status: Frozen v1, 2026-11-05.** Any wire change from here is a version bump (section 7), not an edit.
JSON Schemas live in `protocol/schemas/` (generated by `protocol/gen_schemas.py`); language-neutral test vectors in
`protocol/test-vectors/` (generated by `protocol/gen_test_vectors.py`). Where this text and a schema disagree, that
is a bug: fix it, do not guess.

Parties:
- **Server**: the `borrowed-hands` Hermes plugin running inside `hermes gateway run` (Railway, Hermes v0.22.7).
- **Helper**: the `bh` daemon on a Mac, running as the logged-in user. It dials out; the server never dials in.
- **Dispatcher and runner**: `bh-dispatch` (root, reached by one pinned sudoers rule) starts `bh-runner` as uid
  `bh-builder` in a system-domain LaunchDaemon (`docs/SANDBOX.md`). They never speak this protocol; their JSON
  contracts are in SANDBOX.md and SPEC section 9.

Trust model: the helper's local config (grants) is the authority for what may run, and every security decision is
enforced on the Mac, in code, outside any model's reasoning. Hermes approval is UX and an audit link, not a security
boundary: it is bypassable by `--yolo`, `approvals.mode: off`, `cron_mode: approve` and `ctx.dispatch_tool` (verified against
Hermes v0.22.7; `tests/plugin/test_hermes_approval.py` exercises the approval path). TLS terminates at the Railway edge, so the edge sees
plaintext. Every application-layer message is therefore signed by its sender, carries an expiry and is
replay-protected, and the server identity is pinned at pairing. Residual risks are listed in section 8.

## 1. Transport

| Item | Value |
|---|---|
| Endpoint | `wss://<host>/bh/v1/ws` (HTTP GET upgrade). `ws://` only to `127.0.0.1`/`localhost`, and only with helper flag `--insecure-local` (tests). |
| Subprotocol | Helper sends `Sec-WebSocket-Protocol: bh.v1`; server must echo it or the helper closes. |
| Health | `GET /bh/v1/healthz` returns `200 {"ok":true,"v":1}`. No other HTTP routes. |
| Frames | Text frames only, UTF-8 JSON. A binary frame closes the socket with 1003. |
| Max frame | 16 MiB (16777216 bytes), both directions. Server: `aiohttp.web.WebSocketResponse(max_msg_size=16777216)`, app `client_max_size` the same. Helper client: `max_msg_size=16777216`. Railway carried 31 MB frames in the spike, so 16 MiB has margin. A sender that would exceed it must truncate (logs) or fail the request with `internal_error`/`frame_too_large`. |
| Heartbeat | WebSocket ping every 20 s from both sides (`heartbeat=20` in aiohttp server and client). aiohttp closes the socket if the pong is late, which gives half-open detection within about 30 s. Additionally the helper treats 45 s with no inbound frame or pong as dead and reconnects. Railway's idle timeout is 600 s, so pings also keep the edge open. |
| Libraries | Server: `aiohttp` (present in the Hermes image through the `messaging` extra, proven on Railway) and `cryptography` (core Hermes dependency, `cryptography==50.0.2`, `pyproject.toml:117`). The plugin adds no dependencies. Helper: `aiohttp>=3.9,<4` and `cryptography>=42,<51`; the dispatcher and runner are stdlib-only `/usr/bin/python3`. |

### 1.1 Close codes

| Code | Meaning | Helper reaction |
|---|---|---|
| 1000 | Normal | Reconnect with backoff |
| 1001 | Server going away (unload, redeploy) | Reconnect with backoff |
| 1003 | Binary or unparseable frame | Reconnect with backoff, log a bug |
| 1009 | Frame too large | Reconnect with backoff, log a bug |
| 4400 | Protocol violation (schema, bad seq, bad frame signature) | Reconnect with backoff |
| 4401 | Auth failed: unknown helper_id or bad device signature | **Stop.** Print "server does not recognise this Mac; run `bh pair` again" |
| 4403 | Helper revoked (unpaired) | **Stop.** Delete pins, print "unpaired by server" |
| 4408 | Handshake timeout (10 s) | Reconnect with backoff |
| 4409 | Superseded: a newer connection for the same helper_id authenticated | Do not reconnect from this process. If another local process holds the connection, exit. |
| 4410 | Pairing code invalid, expired or used | **Stop.** Print "pairing code rejected" |
| 4429 | Rate limited | Reconnect no sooner than `retry_after_s` from the `error` frame, else 60 s |

### 1.2 Reconnect

Full-jitter exponential backoff: `delay = uniform(0, min(60, 1 * 2**attempt))` seconds, where `attempt` starts at
0 and increments on every failed connect or handshake. Reset `attempt` to 0 once a session has stayed
authenticated for 60 s. With a volume attached, Railway does not overlap deploys, so a redeploy or restart gives
about 18 to 19 s of 502s (measured in a Railway spike; about 8.9 s without a volume).
This backoff reconnects within about 20 to 40 s of that. Never reconnect after 4401, 4403 or 4410.

### 1.3 Handshake (normal connection)

```
helper                                   server
  |---- WS upgrade (bh.v1) ----------------->|
  |<--- hello ------------------------------|  server_nonce, server_key_id, server_time
  |---- auth ------------------------------->|  helper_id, client_nonce, device_sig
  |<--- auth_ok -----------------------------|  sid, server_sig, catch-up info
  |---- caps (signed frame, seq 1) --------->|
  |---- jobs.sync (signed frame, seq 2) ---->|
```

1. Server sends `hello` (unsigned envelope): `{"server_nonce": b64u(32 random bytes), "server_key_id", "server_time_ms", "max_frame": 16777216, "v": 1}`.
2. Helper checks `server_key_id` equals its pinned key id. If it differs, close and print "server key changed; re-pair" (stop).
3. Helper sends `auth`: `{"helper_id", "client_nonce": b64u(32), "device_sig"}` where
   `device_sig = Ed25519(device_key, "bh1/auth-device\0" || C({"client_nonce","endpoint","helper_id","server_key_id","server_nonce"}))`
   and `endpoint` is the exact wss URL the helper dialled.
4. Server looks up `helper_id` (must exist, not revoked), verifies `device_sig` with the stored device public key
   and checks `endpoint` equals its own configured public URL. Failure: close 4401.
5. Server mints `sid` (uuid4) and replies `auth_ok`: `{"sid", "server_sig", "server_time_ms"}` with
   `server_sig = Ed25519(server_key, "bh1/auth-server\0" || C({"client_nonce","helper_id","server_nonce","sid"}))`.
6. Helper verifies `server_sig` with the pinned server key. Failure: close 4401 locally, stop, print "server failed to prove its key".
7. If an older authenticated connection exists for the same `helper_id`, the server closes it with 4409 **after** step 5.
8. From here on every frame is a signed frame (section 2.2). The helper sends `caps` (seq 1) then `jobs.sync` (seq 2).

`C(x)` is the canonical serialization in section 2.3. `b64u` is base64url without padding (RFC 4648 section 5).
Handshake deadline: 10 s from upgrade to `auth_ok`, else 4408.

## 2. Envelope

### 2.1 Unsigned envelope (handshake only: `hello`, `auth`, `auth_ok`, `pair`, `pair_ok`, `error` before auth)

```json
{"v": 1, "p": "<b64u(payload bytes)>"}
```

### 2.2 Signed envelope (every frame after `auth_ok` / `pair_ok`)

```json
{"v": 1, "p": "<b64u(payload bytes)>", "s": "<b64u(Ed25519 signature)>"}
```

`s = Ed25519(sender_key, "bh1/frame\0" || payload_bytes)`. Server frames are signed with the server key, helper
frames with the device key. The verifier checks the signature over the **received bytes**, then parses them. It
never re-serializes to verify.

### 2.3 Payload (`protocol/schemas/payload.json`; handshake frames use `payload-handshake.json`)

```json
{"type": "job.submit", "id": "<uuid4>", "re": "<uuid4 of the request this answers, optional>",
 "sid": "<uuid4>", "seq": 7, "ts": 1793861063968, "exp": 1793861183968, "body": { }}
```

| Field | Rule |
|---|---|
| `type` | One of the message types in section 5. Unknown type: reply `error` `invalid_arguments`, do not close. |
| `id` | uuid4, unique per sender per session. A receiver keeps the ids of the current session and closes 4400 on a repeat. |
| `re` | Present on every reply. |
| `sid` | Required after the handshake. Must equal the session id from `auth_ok`/`pair_ok`. Mismatch: close 4400. Because `sid` is signed, a frame from one session cannot be replayed into another. |
| `seq` | Required after the handshake. Per-direction counter starting at 1, strictly +1. Gap or repeat: close 4400. This defeats replay and reordering by the edge. |
| `ts` | Sender clock, unix ms. |
| `exp` | Required after the handshake. Unix ms, `ts < exp <= ts + 120000`. The receiver rejects (close 4400) if `now > exp + 60000` (60 s clock-skew allowance) or the window exceeds 120 s. |
| `body` | Type-specific object (schemas in `protocol/schemas/`). |

**Canonical serialization `C`.** `C` is RFC 8785 (JSON Canonicalization Scheme) restricted to an input subset
in which RFC 8785 and the one-line Python form below produce identical bytes:

| Rule | Why it matters |
|---|---|
| Object keys match `[a-z0-9_]+` | RFC 8785 sorts keys by UTF-16 code units; for ASCII keys that equals Python's code-point sort. |
| Numbers are integers in `[-(2**53-1), 2**53-1]`; no floats, exponents or `-0.0` | RFC 8785 number serialization (ECMAScript `Number.toString`) and Python agree on integers in this range. Times and durations are integer ms. |
| Strings are valid Unicode (no lone surrogates) | Both emit UTF-8. Both escape only `"`, `\` and U+0000 to U+001F, using `\b \t \n \f \r` and lowercase `\u00xx` for the rest; everything else (including U+007F, `/` and non-ASCII) is literal. |
| No duplicate keys; no NaN or Infinity; no trailing data | Parsers reject them (Python: `object_pairs_hook`, `parse_float` raising, `parse_constant` raising). |
| No insignificant whitespace; `true`, `false`, `null` lowercase | As RFC 8785. |

Reference implementation, both sides:
`json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False, allow_nan=False).encode("utf-8")`
after validating the subset. Python is the only implementation in 0.1. Any other implementation must reproduce
every vector in `protocol/test-vectors/vectors.json` (canonical bytes, rejects, Ed25519 signatures, fingerprints,
key ids, pairing string).

Signatures are always verified over the bytes **as received** (sections 2.2 and 4.1), so a canonicalization
difference between implementations can only make verification fail, never make a forgery pass. Canonical bytes are
produced for frames, contracts, handshake signature inputs and `contract_hash`.

### 2.4 Errors (`protocol/schemas/error.json`)

Every failed request is answered by `type: "error"` with `re` set:

```json
{"code": "needs_grant", "message": "human readable, no internal paths", "detail": {"...": "optional"}, "retry_after_s": 30}
```

`code` enum (closed set; adding one is a protocol version bump):

| Code | Meaning |
|---|---|
| `denied` | A person or policy said no: device-confirm declined, Hermes approval denied, grant explicitly revoked, approval ticket missing. |
| `needs_grant` | No grant covers it yet; the owner can add one on the Mac. `detail.hint` holds the exact `bh grant ...` command. Also used for scheme, configuration or destination outside the grant's allowlist. |
| `helper_unavailable` | No connected helper matches, the capability is disabled on the Mac, or the server listener is not running. |
| `helper_busy` | The Mac has one active build and 3 queued (`detail.reason: "queue_full"`, `retry_after_s` an estimate). Retry later or cancel a job. |
| `invalid_arguments` | Malformed request: schema failure, unknown helper_id, bad sha, bad requirement string, unsafe checkout tree (`detail.reason: "unsafe_tree"`). |
| `expired` | Contract `expires_at` passed before the job started, or a pairing code expired. |
| `replay` | `job_id` or `nonce` already seen with a different contract hash, or a frame seq violation reported before closing. |
| `timeout` | Build exceeded its wall-clock limit, or a request got no reply within its deadline. |
| `cancelled` | Cancelled by the agent (`hands_job cancel`), the Mac (`bh cancel`), revocation or unpair. |
| `needs_resolution` | The agent must fix something in the repo: commit not found on the configured remote (`commit_not_found`), not reachable from `refs/heads/bh/*` (`not_on_bh_branch`), repo fingerprint mismatch (`repo_mismatch`), project path missing at that commit (`project_missing`), or remote Swift package dependencies, which 0.1 cannot resolve (`unsupported_dependencies`, with `detail.files` and the fix: vendor the package as a local path package). |
| `internal_error` | Anything else, including helper restart mid-job (`helper_restarted`), resource budgets exceeded on the Mac (`disk_budget`, `memory_budget`, `budget_check_failed`) and dispatcher errors (`dispatch_error`). |

## 3. Pairing

### 3.1 Pairing string

```
bh1:<endpoint>#<code>.<server_pubkey>
```

- `endpoint`: the exact `wss://host[:port]/bh/v1/ws` URL. It must not contain `#`.
- `code`: b64u of 16 random bytes from `secrets.token_bytes(16)`, so 22 characters and 128 bits.
- `server_pubkey`: b64u of the 32-byte raw Ed25519 public key, so 43 characters.
- `server_key_id` (used elsewhere) = first 16 hex chars of `sha256(raw server pubkey)`.

Parse: require the prefix `bh1:`, then `rpartition("#")`, then split the fragment on the single `.`. Validate the
lengths and alphabet (`[A-Za-z0-9_-]`) and that the endpoint starts with `wss://` (or `ws://127.0.0.1`/`ws://localhost`
with `--insecure-local`). Example:
`bh1:wss://hermes.example.com/bh/v1/ws#q9Xz0nKc3vT1aB7dE2fG4h.Zm9vYmFyYmF6cXV4cXV1eHF1dXhxdXV4cXV1eHF1dXg`

The string travels only in the owner's authenticated chat (an independent channel from the WSS). Anyone holding it
within 10 minutes can pair, which is why it is single-use, short-lived and shown only to configured owners.

### 3.2 Server side code handling

- `/hands pair` (owner-only, see SPEC section 4) creates a code: store `sha256(code_bytes)` (hex), `created_at`,
  `expires_at = now + 600 s`, `used_at = NULL`, `issued_to` (platform:user_id). Creating a new code invalidates
  every unused earlier code (`used_at = 'superseded'`). The plaintext code is never stored or logged.
- Plain SHA-256 is enough because the code has 128 bits of entropy; a slow hash buys nothing.
- Consumption is one SQLite statement inside the `pair` handler:
  `UPDATE pair_codes SET used_at=? WHERE code_hash=? AND used_at IS NULL AND expires_at>?` and the pair succeeds only
  if `rowcount == 1`. Compare via the hash lookup, never a string loop over candidates.
- Rate limit: at most 10 `pair` attempts per minute per source IP (socket peer by default; only with explicit
  `trusted_proxy: railway` or `BH_TRUSTED_PROXY=railway`, use the rightmost edge-appended `X-Forwarded-For`
  entry) and 30 failed attempts per 10 minutes globally. Deployments enabling this trust must restrict ingress to
  that proxy. Every failed pair validation, including noncanonical base64url, counts. Over the limit: `error` `helper_unavailable`
  `detail.reason: "rate_limited"` plus close 4429 with `retry_after_s`. After 30 global failures, also invalidate the
  outstanding code (the owner must run `/hands pair` again).

### 3.3 Pair exchange

Same socket and `hello` as section 1.3, but the helper sends `pair` instead of `auth`:

```
helper -> pair    {"code", "device_pubkey": b64u(32), "device_name", "client_nonce", "helper_version",
                   "os": "macos", "os_version", "arch", "pair_sig"}
         pair_sig = Ed25519(new device key, "bh1/pair\0" || C({"client_nonce","code_hash","device_pubkey","endpoint","server_nonce"}))
         (code_hash = hex sha256 of the code bytes; the plaintext code is in the frame, protected by TLS)
server -> pair_ok {"helper_id": uuid4, "sid": uuid4, "server_sig"}
         server_sig = Ed25519(server key, "bh1/pair-ok\0" || C({"client_nonce","device_pubkey","helper_id","server_nonce","sid"}))
```

Server checks, in order: rate limit; `hello` sent and fewer than 10 s elapsed; schema; `pair_sig` valid for
`device_pubkey` (proves possession); code consumption (section 3.2), else close 4410 with `error` `expired`; insert
the helper row `{helper_id, device_pubkey, device_name, paired_at, paired_by, revoked_at: NULL}`. The helper verifies
`server_sig` against the `server_pubkey` from the pairing string, and only then writes its config (`server.url`,
`server.pubkey`, `server.key_id`, `helper_id`) and pins. If it fails it deletes the new device key and exits 2. The
session then continues as authenticated (seq 1 is `caps`).

**Owner notification.** Plugins cannot message a chat outside a session context (`hermes_cli/plugin_messages.py:1-8`).
The `/hands pair` handler therefore captures its session route, then posts the pairing string with
`ctx.post_message` and keeps the returned handle. On a successful pair, the notifier's `bh-owner-notices` worker
thread calls `handle.edit(...)` (thread-safe, `plugin_messages.py:82`) to replace the string with
"Paired: <device_name> (<helper_id 8 chars>); waiting for Mac to advertise capabilities. Pairing alone grants
nothing." This also removes the secret from the chat where the platform supports edits. If the edit fails (gateway
restarted, surface cannot edit), the notice is queued in the `notices` table and prepended to the next `hands_*` tool
result and to `/hands status`. When the helper later advertises usable grants, the same worker posts a NEW reply to
that route summarizing them (identical caps and reconnects do not repeat it). Routes are memory-only and expire after
24 hours; after a gateway restart a fresh `/hands pair` is needed for these replies. In this standalone build the
edit and reply path is not yet proven on a real chat surface; it is P0 test PL-6.

**Pairing grants nothing.** A freshly paired helper advertises no capabilities: every `[capabilities]` entry
is off and there are no `[[workspaces]]` until the Mac's owner enables them locally (`bh caps enable`,
`bh grant add`). Pairing only establishes the two identities.

### 3.4 Device key storage

The helper generates the Ed25519 device key with `cryptography` and stores the 32-byte private seed (base64url, one
line) in `~/Library/Application Support/BorrowedHands/device_ed25519.key`. Requirements, each with a test:
- The parent directory is created 0700 and owned by the user. On every load, `lstat` must show a real directory (not
  a symlink), owned by the user, mode exactly 0700; otherwise refuse to start ("unsafe permissions on <dir>").
- The key file is created atomically: write to `device_ed25519.key.tmp` opened with
  `O_WRONLY|O_CREAT|O_EXCL|O_NOFOLLOW` and mode 0600, `fsync`, then `rename` over the final name. An existing tmp
  file is an error, not something to overwrite.
- It is loaded with `open(O_RDONLY|O_NOFOLLOW)` and then `fstat`: a regular file, owned by the user, mode 0600,
  `nlink == 1`; otherwise refuse.
- Rotation is section 3.6. The old key file is overwritten via the same atomic path and never kept.
- No Keychain in 0.1: an ACL prompt would block an unattended agent.

Residual risk: any process running as the same macOS user can read this file (and edit the grants in
`config.toml`). Same-user compromise of the Mac is out of scope (section 8).

### 3.5 Unpair

- **From the server:** `/hands unpair <helper_id|name>` (owner-only) sets `revoked_at`, cancels the helper's
  non-terminal jobs on the server side (state `cancelled`, `detail.reason: "revoked"`), sends `unpaired` if
  connected, then closes 4403. A revoked helper_id can never authenticate again.
- **From the Mac:** `bh unpair` sends `unpair` (signed frame) if connected and waits up to 5 s for `ack`, then
  deletes its pins, device key and job database. It always deletes local state, even offline. The server, on
  `unpair`, sets `revoked_at` and queues an owner notice. An offline unpair leaves a stale server row that can never
  authenticate (no key) and that `/hands status` shows until `/hands unpair` removes it.
- On receiving `unpaired` or 4403, the helper cancels running work (runner kill path), deletes pins and the device key,
  and exits 3 ("unpaired by server").

### 3.6 Key rotation

- **Device key:** `bh rotate-key` (connected) generates a new key and sends `device.rotate`
  `{"new_pubkey", "sig_new"}` with `sig_new = Ed25519(new key, "bh1/rotate-device\0" || C({"helper_id","new_pubkey","sid"}))`.
  The frame itself is signed by the old key, so both keys attest. The server swaps the stored key atomically and
  replies `ack`. The helper then swaps locally and reconnects.
- **Server key:** `/hands rotate-key` (owner-only) generates a new key and sends each connected helper
  `server.rotate` `{"new_pubkey", "new_key_id", "sig_new"}` with
  `sig_new = Ed25519(new key, "bh1/rotate-server\0" || C({"new_key_id","new_pubkey","old_key_id"}))`. The frame is
  signed by the old key. The helper verifies both, re-pins, and replies `ack`. Contracts signed by the old key that
  are still queued stay valid (the helper keeps the old key id for 15 minutes only for already-accepted jobs).
  Helpers that are offline at rotation must re-pair; `/hands status` lists them. The old private key is deleted
  after every connected helper has acked or after 15 minutes.

## 4. Signed action contract

Every action request that makes the Mac do something (`system.info`, `screen.capture`, `xcode.build`) carries a
contract signed by the server key. It is independent of the session so it can be persisted, re-verified after a
helper restart, and audited.

### 4.1 Wire form (`protocol/schemas/contract.json`)

`job.submit` body: `{"contract": "<b64u(contract bytes)>", "sig": "<b64u>"}` with
`sig = Ed25519(server_key, "bh1/job\0" || contract_bytes)`. The helper verifies over the received bytes, then
parses. `contract_hash = hex sha256(contract_bytes)`.

```json
{
  "v": 1,
  "job_id": "uuid4",
  "nonce": "b64u(16 random bytes)",
  "helper_id": "uuid4",
  "server_key_id": "16 hex",
  "action": "xcode.build | screen.capture | system.info",
  "params": { },
  "issued_at": 1793861063000,
  "expires_at": 1793861663000,
  "approval_ref": "hermes:<ticket uuid4> | none"
}
```

`params` by action (schemas `params-*.json`):
- `xcode.build`: `{"workspace_id", "repo_fingerprint", "commit", "scheme", "configuration", "destination"}`
- `screen.capture`: `{"display": 1, "max_px": 1600}`
- `system.info`: `{}`

This nests the brief's flat build fields under `params` so all three actions share one header and one check path.

**What a contract binds.** Every signed contract binds the immutable 40-hex commit SHA, the exact execution
parameters (workspace, scheme, configuration, destination), the device (`helper_id`), a unique `job_id` and `nonce`,
and an expiry of at most 10 minutes. A persistent Hermes approval ("session" or "always") covers helper + workspace +
scheme + configuration + destination and never the SHA, so every new commit still gets its own contract. The device
grant is checked independently on every contract, whatever Hermes approved. No approval scope ever implies a broader
workspace or destination: the helper compares exact strings, with no wildcards, prefixes or defaults.

`repo_fingerprint = hex sha256("bh1/repo\0" || normalize(url))`, where `normalize` takes an `https` URL, lowercases
the scheme and host, rejects userinfo, port, query and fragment, strips one trailing `/` and then one trailing
`.git`. Example: `https://GitHub.com/alext8900/Demo.git/` normalizes to `https://github.com/alext8900/Demo`. The
helper computes it from its **local** `remote_url`; Hermes computes it from the URL the agent passes. The helper never
fetches a URL that came from Hermes.

### 4.2 Helper checks, in order (first failure wins; nothing executes before step 11)

1. Frame checks: envelope, frame signature, `sid`, `seq` (section 2.3). Failure: close 4400.
2. `sig` verifies over `contract_bytes` with the pinned server key whose id equals `server_key_id`. Failure: `error denied` (`detail.reason: "bad_signature"`) and log loudly.
3. Contract parses and validates against `contract.json` + the action's params schema (unknown keys rejected). Failure: `invalid_arguments`.
4. `helper_id` equals mine. Failure: `invalid_arguments`.
5. Time: `issued_at - 60000 <= now <= expires_at` and `expires_at - issued_at <= 600000`. Failure: `expired`.
6. Replay: in one SQLite transaction, look up `job_id` and `nonce`.
   - `job_id` exists with the same `contract_hash`: idempotent resend. Reply with the job's current `job.state` (and the result if terminal) and stop here.
   - `job_id` or `nonce` exists with a different hash: `replay`.
   - Otherwise insert the row in state `received` (not yet visible as accepted) and commit. Rows are kept 7 days.
7. Capability enabled locally (`[capabilities]` in config; all off after pairing). Failure: `helper_unavailable` (`detail.reason: "capability_disabled"`).
8. Grant (`xcode.build` only): a `[[workspaces]]` entry with `id == workspace_id` exists and is not expired. Failure: `needs_grant` with hint `bh grant add xcode.build --workspace <id> ...`.
9. Allowlists: `scheme` in `schemes`, `configuration` in `configurations`, `destination` exactly equal to one of `destinations` (and to a destination the dispatcher accepts: exactly `platform=macOS,arch=arm64` or `generic/platform=iOS Simulator`, compile-only). Failure: `needs_grant` (`detail.field`).
10. `repo_fingerprint` equals the fingerprint of the workspace's local `remote_url`. Failure: `needs_resolution` (`detail.reason: "repo_mismatch"`).
11. Device confirm, only if that workspace has `confirm = true` (default false): show a macOS dialog (`osascript display dialog`, 120 s `giving up after`) with action, workspace, scheme, commit and approval_ref. Declined: `denied`. No answer: `denied` (`detail.reason: "device_confirm_timeout"`). Not applicable to `system.info` and `screen.capture`.
12. Capacity: one active build per Mac and a FIFO queue of at most 3. Full: `helper_busy` (`queue_full`).
13. Mark the row `queued`, reply `job.accepted {"job_id", "state": "queued", "position"}`.

At run time (`xcode.build`), the helper dequeues and hands the job to `bh-dispatch` (SPEC 9), which does 15 and 16:
14. On dequeue, re-check `expires_at` and that the grant still exists. Expired: state `expired`. Grant gone: `cancelled` (`grant_revoked`).
15. Materialize, only in bh-runner as bh-builder under `git.sb` (https on port 443 only, writes confined to the job dir): fetch `refs/heads/bh/*` from the local `remote_url` with `--filter=blob:none`, require `merge-base --is-ancestor <commit> <ref>` for some fetched ref, fetch and check out the commit with hooks, filters, submodules and repo config disabled, and verify `HEAD == commit`, `HEAD^{tree} == commit^{tree}` and a clean status. Then, before any build: refuse if the checkout contains a `Package.resolved` with remote pins or a project file with `XCRemoteSwiftPackageReference`. Failures: `needs_resolution` (`commit_not_found`, `not_on_bh_branch`, `project_missing`, `unsupported_dependencies`) or `internal_error`.
16. Build under `builder.sb` (no network, read allowlist, writes confined to the job dir and bh-builder's per-user temp and cache) with code signing off, then `xcresulttool get build-results` under the same profile.

### 4.3 Job lifecycle

```
received --(checks 7-13 pass)--> queued --> materializing --> building --> succeeded
    |                              |             |               |  \----> failed
    +--(check fails)--> [error reply, row kept as failed]        |
                                   +--> expired (step 14)        +--> failed (timeout)
   queued | materializing | building --> cancelled
```

- `materializing` is reserved: in 0.1 the dispatcher reports nothing until it finishes, so the helper goes from
  `queued` straight to `building` when it starts `bh-dispatch`, and covers checkout and build with that one state.
- `succeeded`: xcodebuild exit 0 and result status `succeeded`. `failed`: anything else that ran, including compile
  errors (`error.code` absent, `result.status: "failed"`) and timeouts (`error.code: "timeout"`).
- Terminal states: `succeeded`, `failed`, `cancelled`, `expired`. Terminal rows and results are kept 24 h for
  re-delivery, then pruned (the row id stays 7 days for replay checks).
- `screen.capture` and `system.info` go `queued` to `succeeded`/`failed` directly. They do not wait behind a build:
  they have their own single-slot lane, since they do not touch the runner.
- The helper sends `job.state {"job_id", "state", "at"}` on every transition, and `job.result` on a terminal state.

### 4.4 Results (`protocol/schemas/job-result.json`)

`job.result` body: `{"job_id", "state", "result": {...} | null, "error": {code, message, detail} | null}`.
Helper frames are signed by the device key, so results are attributable. Build result:

```json
{"status": "failed", "duration_ms": 10590, "xcode": "26.1 (17B55)", "destination": "platform=macOS,arch=arm64",
 "error_count": 2, "warning_count": 0,
 "errors": [{"file": "Sources/Greeting.swift", "line": 1, "column": 42, "message": "Cannot find 'undefinedThing' in scope", "type": "Swift Compiler Error"}],
 "warnings": [], "log_tail": "last <= 4000 bytes", "truncated": false}
```

- `line` and `column` are 1-based (the runner already converts xcresulttool's 0-based values; SANDBOX.md "Result").
- `duration_ms` = the dispatcher's `duration_s` x 1000, rounded.
- `file` is relative to the repo root. Absolute paths outside the checkout become `"<sdk>"` or `"<outside>"`; the schema rejects any other leading `/` and control characters.
- At most 50 errors and 50 warnings, each message at most 500 chars, `log_tail` at most 4000 chars.
- **Compiler output is untrusted data.** It comes from a hostile-capable build and goes to a model. It is constrained by structure (the schema, fixed keys) and length (the caps above), and path-scrubbed for hygiene. The scrubbing is not a security boundary: no security decision anywhere depends on its content or on what a model concludes from it. The plugin wraps it in the tool result as data, never as instructions.
- Screen capture result: `{"mime": "image/png", "width", "height", "display", "png_b64"}`, at most 12 MiB of base64.
- System info result: only non-sensitive capability-discovery data: `{"os_version", "os_build", "arch", "cpu", "memory_gb", "xcode": {"version", "build"} | null, "disk_free_gb"}`. No serial numbers, hostnames, user names, paths, network data or uptime. Served only to the authenticated server over the signed session.

### 4.5 Durability and delivery

**Helper** (SQLite `~/Library/Application Support/BorrowedHands/jobs.sqlite3`, WAL, `synchronous=FULL`):
- Every state transition commits before the frame announcing it is sent.
- On helper start: run the runner kill path (kills every bh-builder process), then rows in `materializing`/`building` become `failed` with `internal_error` / `helper_restarted`; `queued` rows past `expires_at` become `expired`; the rest stay queued.
- Undelivered terminal rows (`delivered = 0`) are re-sent after every authentication through `jobs.sync`
  `{"active": [{"job_id","state"}], "results": [<job.result bodies>]}`. The server answers `job.ack {"job_ids": [...]}`
  only after committing them, and the helper sets `delivered = 1` on ack.

**Server** (SQLite under the plugin data dir, see SPEC section 7):
- The contract and `contract_hash` are committed **before** `job.submit` is sent. Before attempting the write, the
  server durably marks state `submitted` (delivery uncertain), retaining the `pending_send` flag until the write
  succeeds or a helper state/result confirms receipt. If the write fails, identical bytes are resent on the helper's
  next authentication. Identical bytes make the resend idempotent (step 6), so "maybe sent" is safe. A write attempt
  can never be cancelled locally as unsent; cancellation requires the helper's confirmation.
- On plugin restart: non-terminal jobs keep their last known state, marked `stale`. They are reconciled from the
  next `jobs.sync`. A server job the helper does not report in `active` or `results` within 30 s of `auth_ok`, whose
  contract has expired, becomes `failed` / `internal_error` / `lost`.
- `job.result` handling is idempotent: the first terminal result wins, later duplicates are acked and ignored.

### 4.6 Disconnects, cancel and revoke

- **Disconnect mid-job:** the helper keeps running the job and buffers state and result. The server marks the job
  `detached` (an overlay, not a state). `hands_job` reports "helper offline since <t>; last state <s>". Nothing is
  cancelled because of a disconnect.
- **Cancel:** `job.cancel {"job_id"}` (signed frame; no contract needed since it only removes work). For a queued
  job: drop it, state `cancelled`. For a running build: the helper sends SIGTERM to its `sudo bh-dispatch` child.
  bh-dispatch treats SIGTERM/SIGINT as cancel: it boots the LaunchDaemon out, sweeps every uid-470 process from a
  child that has dropped to uid 470, and prints one JSON line with `status: cancelled` (SANDBOX.md, "Cleanup"). The
  helper waits for that line up to the dispatcher's own deadline. A SIGTERM sent by the owner's uid reaches the
  root dispatcher through sudo (verified; SANDBOX.md and `tests/cancel_owner.py`). For a helper that lost its child,
  the pinned `bh-dispatch --cancel` sudoers entry signals the in-flight dispatcher for exactly that job. State `cancelled`. Reply `ack`; the terminal state follows as `job.result`.
  Cleanup is deterministic: the dispatcher's post-job sweep and build-dir removal run on every exit path.
- **Revoke mid-job:** `unpaired` or 4403 runs the cancel path for every job, then unpair cleanup (3.5). A local
  `bh grant revoke <workspace>` cancels that workspace's queued and running jobs with `cancelled`
  (`detail.reason: "grant_revoked"`), and later submits get `needs_grant`.
- **Result re-delivery:** see 4.5. The server answers the agent from its own DB, so `hands_job` works while the
  helper is offline, and a result that arrives late is visible on the next `hands_job` call.

## 6. Capabilities and matchmaking

### 6.1 `caps` body (`protocol/schemas/caps.json`)

Sent at seq 1 and again whenever local config changes (the helper watches the config file mtime):

```json
{"helper_version": "0.1.0", "name": "Alexs MacBook Pro", "os": "macos", "os_version": "26.2", "arch": "arm64",
 "busy": false, "queue_depth": 0,
 "capabilities": [
   {"name": "system.info", "v": 1},
   {"name": "screen.capture", "v": 1, "displays": 1},
   {"name": "xcode.build", "v": 1, "xcode": "26.1", "xcode_build": "17B55",
    "workspaces": [{"workspace_id": "demo", "repo_fingerprint": "<64 hex>", "schemes": ["Demo"],
                    "configurations": ["Debug"], "destinations": ["platform=macOS,arch=arm64"], "expires_at": null}]}]}
```

A capability appears only if it is enabled locally **and** usable: `xcode.build` needs `xcode-select -p` to resolve
and the production sandbox install to be present (`/opt/borrowed-hands/bin/bh-dispatch` root-owned, no
`/opt/borrowed-hands/TEST_MODE`, empty `libexec/profiles/`, the pinned sudoers rule working); `screen.capture` needs
its capture path to report the Screen Recording permission (SPEC 9.5). The workspace `remote_url` is never sent,
only its fingerprint.

### 6.2 Requirement language (`hands_find(requires=[...])`)

```
req      := cap_name | key op version | key "=" word
cap_name := "system.info" | "screen.capture" | "xcode.build"
key      := "os" | "arch" | "os_version" | "xcode"
op       := ">=" | "="
version  := digits ("." digits){0,3}
```

- `os=macos`, `arch=arm64` or `arch=x86_64`: exact, case-insensitive match.
- `os_version>=15.0`, `xcode>=16`: compare as integer tuples padded with zeros (`16` equals `16.0.0`). `=` on a version is exact tuple equality.
- `xcode` and `xcode>=...` imply `xcode.build`.
- All requirements are ANDed. At most 8 per call, each at most 64 chars. Anything else is `invalid_arguments`, with the offending string.
- Evaluated by the plugin against the latest `caps` of each paired helper. Offline helpers are excluded unless `include_offline: true`.

## 7. Versioning

`v` in the envelope, the payload and the contract is `1`. A peer that receives another `v` replies `error`
`invalid_arguments` (`detail.reason: "unsupported_version"`) and closes with 4400. Schemas use
`additionalProperties: false`, so any field change bumps `v`, regenerates the schemas and the test vectors, and needs
Alex's sign-off. Hackathon scope: no negotiation.

## 8. Residual risks (accepted for 0.1)

- **Server signing-key compromise.** Whoever holds `server_ed25519.key` (the Railway volume, or anyone with shell
  access to the deployment) can mint valid contracts and frames for every paired Mac. The Mac still enforces its
  grants, allowlists and the sandbox, so the attacker gets exactly what the grants allow: builds of granted
  workspaces' commits that are on `bh/*` branches, captures if enabled, and system info. Mitigations: `/hands
  rotate-key`, `bh unpair` on the Mac, and narrow grants. There is no revocation list for a stolen server key in 0.1;
  rotation plus re-pairing is the response.
- **Same-user compromise on the Mac.** Malware running as the Mac's user can read the device key, edit `config.toml`
  grants and impersonate the helper. Out of scope; the sandbox protects the user from builds, not the other way round.
- **Railway edge.** It cannot forge or replay frames (signatures, seq, sid, exp), but it can drop or delay them and
  see their contents (repo fingerprints, schemes, diagnostics, screenshots). Confidentiality from the hosting provider
  is not a 0.1 goal.
- **Hostile DNS for the git remote.** It can choose which public address git talks to; the tree check makes that
  equivalent to a hostile remote (SANDBOX.md "Ship decision: DNS rebinding").
- **Build metadata reads.** A build can stat known paths outside its allowlist (SANDBOX.md gap 1).
- **Diagnostics content.** Compiler output is attacker-influenced text shown to a model; constrained and scrubbed,
  never trusted (section 4.4).
